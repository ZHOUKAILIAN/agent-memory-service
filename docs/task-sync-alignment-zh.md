# 任务同步对齐文档

这份文档用来先对齐一件事：`agent-memory-service` 接下来要解决的核心问题，不只是“存项目记忆”，而是让不同平台、不同端、不同 Agent 能围绕同一个任务或需求持续同步信息。

这是一份 `what / why / 部分 how` 文档，不直接进入详细实现。

## 我们要解决的是什么

我们要支持下面三类核心场景：

1. 单平台多 Agent
2. 多平台多 Agent
3. 多端多 Agent

这三类场景的共同点是：

- 不同 Agent 可能不是同一个产品
- 不同 Agent 可能运行在不同平台
- 不同 Agent 可能运行在不同设备
- 但它们需要继续同一个任务或需求

换句话说，我们真正要同步的对象，不应该只是“某个项目”，而应该是“某个任务或需求在一段时间里的共享工作状态”。

## 为什么要先对齐这个问题

如果这个问题不先讲清楚，后面很容易做偏：

- 只做成“项目聊天记录存档”
- 只支持单一 Agent
- 只能在一个终端里续跑
- 同步了很多内容，但真正关键的信息没有沉淀下来

我们需要的不是一个“对话备份箱”，而是一个“任务协作记忆层”。

## 场景定义

### 1. 单平台多 Agent

例子：

- 都在本地开发环境里
- 先用 Codex
- 再切到 Claude Code
- 最后再让 OpenClaw 接着做

目标是让不同 Agent 在同一个平台内协作时，不需要每次重新解释背景。

### 2. 多平台多 Agent

例子：

- 本地用 Codex 做开发
- Web 端用另一个 Agent 看方案
- 远端服务器上跑一个自动修复 Agent

目标是让同一个任务能跨运行平台连续推进。

### 3. 多端多 Agent

例子：

- Mac 上开始做需求
- 手机上补充说明和确认方向
- 办公室另一台机器继续编码

目标是让任务状态能跨设备延续，而不是绑定在某一台机器上。

## What：到底要同步什么

这里最重要的第一条不是“同步哪些字段”，而是“同步粒度”。

还需要补充一点：任务记忆本身也要分层。默认进入上下文的应该是概要，详细信息应该按需加载。

## 一、同步粒度

如果要支持“某个任务或者需求”的协同，我们至少要区分三层：

### `project`

表示长期存在的工程上下文，例如：

- 某个仓库
- 某个产品线
- 某个长期项目

### `task`

表示一次明确的需求、缺陷、任务或工作项。

例子：

- 修复登录回调漏洞
- 实现订单页筛选功能
- 调查线上慢查询问题

### `session`

表示某一次具体的 Agent 运行或人机协作过程。

例子：

- 这次 Codex 会话
- 这次 Claude Code 会话
- 这次 OpenClaw 的自动执行

结论是：

- `project` 解决长期背景
- `task` 解决本次要继续的工作对象
- `session` 解决一次执行过程的记录

如果只有 `project`，那后面所有任务都会混在一起，信息会越来越脏。

## 二、同步信息类型

围绕一个 `task`，推荐同步的信息分成下面几类。

### 1. 任务身份信息

用于回答“我们现在到底在做哪件事”：

- `task_id`
- `title`
- `type`
- `source`
- `external_ref`

其中 `external_ref` 可以对应：

- ONES 需求单
- GitHub issue
- Jira ticket
- 用户手工定义的任务编号

### 2. 任务目标与背景

用于回答“为什么做这件事”：

- 用户目标
- 业务背景
- 当前问题描述
- 成功标准
- 上下游依赖

### 3. 当前状态

用于回答“现在做到哪了”：

- `todo`
- `in_progress`
- `blocked`
- `done`
- 最近更新时间
- 当前负责人或当前活跃 Agent

### 4. 决策与约束

用于回答“有哪些不能忘的结论”：

- 已确认方案
- 明确不做什么
- 技术约束
- 产品约束
- 安全要求
- 兼容性要求

### 5. 交接摘要

用于回答“下一个 Agent 接手时应该先知道什么”：

- 这轮做了什么
- 没做完什么
- 下一步建议
- 当前阻塞点
- 风险提示

### 6. 关键产物引用

用于回答“相关证据和产物在哪里”：

- 分支名
- PR 链接
- 提交 hash
- 文档链接
- 截图链接
- 日志链接
- 重要文件路径

这里同步的是“引用”优先，而不是把大文件本身全塞进去。

### 7. 事件流

用于回答“这件事是怎么演进到现在的”：

- session 开始
- session 结束
- 状态变化
- 决策形成
- 关键错误
- 关键修复

事件流用于追溯，但不应该无限膨胀。

## 三、哪些东西不应该默认同步

默认不应该全量同步：

- 完整聊天全文
- 超长终端日志
- 完整 diff
- 大段代码
- 敏感配置
- token、cookie、密码、私钥

原因很简单：

- 噪音太大
- 体积太大
- 敏感风险高
- 真实有价值的信息反而被淹没

## Why：为什么需要同步这些信息

同步这些信息，不是为了“存档”，而是为了降低协作损耗。

### 1. 降低重复解释成本

用户不应该在每次切换 Agent 时都重新讲一遍背景。

### 2. 降低上下文丢失

关键决策、约束、状态和待办，不能只活在某一次聊天里。

### 3. 支持真正的交接

下一个 Agent 接手时，应该直接看到：

- 这件事是什么
- 现在做到哪
- 为什么这么做
- 下一步该做什么

### 4. 支持跨平台跨设备延续

任务不应该绑定在某个工具、某个终端、某台机器上。

### 5. 支持后续自动化

只有先把任务状态结构化，后面才可能做：

- 自动 checkpoint
- 自动提醒
- 自动压缩
- 自动恢复上下文

## 部分 How：怎么同步

这里先对齐原则，不展开到实现细节。

## 当前技术路线选择

这一点现在先明确下来：

- 服务端共享层使用 `PostgreSQL`
- 本地 bridge 使用 `SQLite`

原因是：

- 我们要支持跨 Agent、跨平台、跨设备同步
- 这种场景需要一个稳定的中心共享真相源
- `PostgreSQL` 更适合承载共享任务数据、并发写入和后续扩展
- `SQLite` 更适合本地缓存、outbox、context cache、全文检索和离线补偿

所以这里不是二选一，而是分层使用：

```text
server shared source of truth -> PostgreSQL
local bridge/cache/outbox -> SQLite
```

## 一、同步模型

推荐采用“三段式同步”：

1. 开始读
2. 过程中轻量记
3. 结束写交接

### 1. 开始读

每次任务开始前，先读取当前 `task` 的共享上下文。

目标是让当前 Agent 先知道：

- 任务目标
- 当前状态
- 最近决策
- 下一步待办

### 2. 过程中轻量记

任务进行中，不必同步每一句话，只记录关键变化：

- 状态切换
- 明确决策
- 关键产物
- 关键失败

### 3. 结束写交接

每次会话结束时，生成一份结构化交接摘要。

这一步是整个体系里最重要的同步动作。

## 二、同步入口

推荐提供统一 bridge，而不是每个 Agent 各接一套。

bridge 可以有两个入口：

- `MCP`
- `CLI`

原因是：

- 支持 MCP 的 Agent 可以直接工具化接入
- 不支持 MCP 的运行时可以走 wrapper 或脚本

## 三、同步单位

推荐以 `task` 为主同步单位，而不是直接以 `project` 为唯一单位。

建议关系是：

```text
project
  └── task
        └── session
```

其中：

- `project` 提供长期背景
- `task` 承载当前需求或工作项
- `session` 记录一次次执行过程

## 四、同步原则

### 原则 1：摘要优先

优先同步可复用的摘要，不优先同步原文。

### 原则 2：结构化优先

优先同步状态、决策、待办、约束，而不是散落聊天。

### 原则 3：引用优先

优先同步链接、路径、提交号、分支名，不优先搬运大对象本体。

### 原则 4：显式交接优先

最重要的同步点是“这轮结束时留下什么给下一轮”。

### 原则 5：失败可补偿

同步失败时，数据不应该直接丢失，应该允许后续补传。

## 用户怎么接入

这个问题也要先对齐成产品视角，而不是接口视角。

对用户来说，应该尽量像这样：

1. 绑定一个仓库或任务来源
2. 系统自动识别当前 task
3. 开始任务时自动拉上下文
4. 结束任务时自动或半自动写交接

用户不应该长期手工处理：

- `projectId`
- 各种底层 API 调用
- 每轮都手工说“帮我同步一下”

## 还需要额外对齐什么

除了你提的 3 个问题，我觉得至少还要再对齐下面 5 件事。

### 1. 以什么为主键同步

到底是按：

- `project`
- `task`
- 外部工单号
- repo + branch

做绑定。

这是最核心的建模问题。

### 2. 谁是状态真相源

比如：

- 任务状态以 memory service 为准
- 还是以 ONES / issue 系统为准
- 还是只是做缓存和补充说明

这个不对齐，后面状态会打架。

### 3. 冲突怎么处理

如果两个 Agent 同时推进同一个任务：

- 谁覆盖谁
- 是否保留并行 session
- 最终如何汇总

这个需要在模型层就考虑。

### 4. 安全边界是什么

哪些内容允许同步，哪些内容必须脱敏或禁止上传。

### 5. 失败和重试怎么做

如果：

- 服务不可用
- 网络失败
- 远端超时
- 本地崩溃

那同步内容怎么暂存、重试和恢复。

## 当前对齐结论

如果先压缩成一句话，当前最应该对齐的是：

`agent-memory-service` 接下来不是只做项目级记忆，而是要支持围绕某个 task/requirement 的跨 Agent、跨平台、跨设备协作同步。

因此后续设计应优先围绕这几个问题展开：

1. `project / task / session` 三层模型
2. 任务记忆的 summary / detail / raw event 分层
3. 任务级状态、决策、待办、交接摘要
4. 开始读、过程记、结束写 的折中同步模式
5. MCP + CLI 的统一接入层
6. 失败补偿、冲突处理、安全边界
